## 核心观点（15 条）

1. **用最新最强的模型**。其他都可能是浪费时间。模型 10% 出错你不知道是哪 10%，只能反复尝试。便宜 50% 但随机变笨 20% 的通才不值得雇。「还有谁在用 Opus 4.5？」

2. **别再担心堆积 slop**。「会把代码库变成烂摊子」这话半年前也许对，现在他不信 agent 真会加 slop，就算加也不信结果就无法维护。

3. **提示写「做什么」不写「怎么做」**。描述想要什么而非怎么实现，结果往往更好。例：「把字节码编译器和 VM 做到最快，不到 2 倍不要停。」

4. **让整个 SDLC 对 agent 可读**。止住幻觉的是工具调用——让 agent 触碰现实；看不到的东西它就编。所以让它端到端运行、读生产日志、部署、看灰度、切版本、翻 flag、分诊 bug、给客户发邮件。你能看到的它都该看到。

5. **给它配套 SDLC 的工具**。自定义插件：bug 报告、发邮件、「系统健康吗？」、发放 feature flag。

6. **给 agent 的知识做 eval**。AGENTS.md / skill / 脚本 / 文档越堆越多，但 agent 真用到了吗？开五个「盲」agent 做对照组 vs 实验组去验。agent 极擅长跑实验。

7. **本地开发现在让人嫌弃**。每个 agent 都该能自行安装运行所需之物，远程机器容易、本地恶心；多 agent 端到端测试时本地容易撞资源冲突。

8. **别跟 agent 一起迭代，让它造工具来迭代**。不是「试这个…不行试那个」，而是「生成 20 个变体 + 一个小页面让我组合测试」。不只解空间，问题空间也适用：「给我 4 个它为什么慢的理论，四个都验」。

9. **要求无可辩驳的证据**（最大的转折点）。agent 擅长产出证据：端到端演练、演示视频、前后对比数字。要建立信任与直觉。把「这不算证据」写进 AGENTS.md。

10. **别等 agent，让它们等你**。在意 TTFT 多半是做错了。拥抱异步，给更大任务、更大野心，批量而非来回。

11. **自动化 / 定时 / 唤醒 / 心跳是杀手级功能**。一旦关掉无比想念。「2 小时后查日志」「上线了告诉我」「每天 9 点查一次」。

12. **别再手动管理上下文**。纠结「用了 300k 还是 380k token」是浪费时间。compaction 效果极好。一个线程 = 一个任务（有的 46 条消息，有的 3714 条）。

13. **线程就是公司的记忆**（在 Amp 里）。「我们当初为什么这么做？」团队越用知识越成倍增长；线程连着 git commit，避免重复劳动。

14. **别让 agent 写给人看的东西**。例外：调试步骤、事故报告、部分文档——那些机械性、另一头是谁不太要紧的内容。

15. **只审影响面大（blast radius）的代码**。核心文件不到 5 个，只看那些；数据库迁移要看。闭包还是类、更漂亮的类型、变量名、甚至重复——不在乎了。判据：能跑吗？能在「框图箭头」层面看懂吗？agent 端到端测过吗？一个月后还能改吗？
